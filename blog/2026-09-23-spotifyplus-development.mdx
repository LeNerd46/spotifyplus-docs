I always knew from the start, when I first started working on Spotify Plus back in May 2025, that this is what I ultimately wanted to build. It was never just about single features I could add to Spotify. I wanted something where anyone could make anything they wanted. A Spicetify for mobile. I knew it was ambitious, but I wanted to make it a reality.

Obviously if you read that date, and you see when this blog post is being written, you'll see it took a while. That's for a few different reasons. Mainly it's a very large task, and I haven't always had the motivation to work on Spotify Plus. But alas, here we are. I am almost ready for the marketplace version of Spotify Plus to be released. The core framework is in place, I just have to write some extensions to replace the main features that the original Spotify Plus had. And I need to do bug testing. There are so many parts to this project, and it's incredibly difficult to make sure that every piece works exactly as intended. And given that some features of the original Spotify Plus can't cleanly be translated to this version of Spotify Plus (ahem, *themes*), this will likely be a pre-release, mainly intended for developers to try out any ideas they have. I want to make sure the API is solid and reliable before replacing the entirety of Spotify Plus with something completely different.

## Why Switch To Scripting

Yes yes, why did I want to move away from the traditional Xposed mod with concrete features in place. As you may or probably may not know, I originally wanted to make all of this because of one single Spicetify extension. It was called Beautiful Lyrics, and it was made by SurfBryce, or SoCalifornian, I'm not entirely sure what he goes by. He made this incredible extension that makes lyrics for Spotify word by word instead of Spotify's normal line by line lyrics. This completely changed how I viewed music and how much of an impact such a seemingly simple project can make. At this point in time, I actually had never looked at Apple Music, so it seemed magic to me. I had to know how it worked. Eventually I decided I wanted to try to build this for mobile, that way I could have beautiful lyrics everywhere I went. This was the start of the biggest project I had ever undertaken. At this point, the only language I knew was C#, so obviously I used .NET MAUI. It was an incredible learning experience, and I am very grateful for the experience I had there. And hot take, when it works, .NET MAUI is actually really nice. Keyword, when it works. The bugs can be incredibly annoying. But when it works, I actually really enjoy the development workflow. Anyways, that was a standalone app. 

One day, I found out about SnapEnhance. I don't even remember how I found out about it, but it introduced me to the Android modding scene. It fascinated me that you could do whatever you wanted inside of an app. And then they released version 2.0 of SnapEnhance, which included a scripting engine. Anyone could write JavaScript to run code inside of Snapchat. This absolutely blew my mind. From that day on (or maybe shortly after, I don't remember. This was in 2024), I knew what I wanted to build. I wanted to make something like Spicetify, but for mobile. I cannot thank SurfBryce and the developers of SnapEnhance enough for leading me to make this project. Projects that you make really can have such a big impact on people, and I hope one day maybe one of my projects can have a similar effect for someone.

## Technical Details

If you're interested in the technical side of how the extension platform works, then you can read this section. Originally I was going to use what SnapEnhance used, which is called Rhino. It's a JavaScript runtime built for embedding. It works pretty nicely with Java. You can define JavaScript objects and you can pretty easily convert objects between the two languages. This worked, but it had many limitations. Again, my dream was to have something as customizable as Spicetify. Rhino is built on hella ancient version of JavaScript. So you are incredibly limited in what you can do even there. TypeScript can alleviate some of that, as you can write modern TypeScript and it will compile it into that ancient version, but the runtime itself is still limited. It's not a browser, and it's not node.js. It's just straight, plain JavaScript. So very limited in what you can actually program. Second big limitation, UI. Writing UI would be incredibly difficult. That's probably one of the coolest things you could theoretically do with a project like this! I did find a solution to this, even if it's a little jank. You could write your UI in XML, compile it into an APK, and load it through your JavaScript. But this wasn't very nice. You can take my word for it.

So what do you do to fix this? Well, I found this project called `nodejs-mobile`. It allows you to embed a node.js runtime inside of your Android app. This means modern JavaScript features, you can use any npm package you want, and you can pretty much do whatever you want. This seemed like the clear winner. However, nodejs-mobile cannot talk to your native Java code as easily as Rhino could. Now at the time, I was not super familiar with React Native. I didn't realize this was a solved issue already. But I eventually found out about JNI, and that communication between node and Android wouldn't be too hard. But that still leaves the issue of UI. How does one create UI in an extension? Well, now that we're using a modern JavaScript engine, we can use a modern standard. React lets you create your own implementation of React. You can define everything about how it works, and what components are available. This seemed like the obvious solution for my problem. The only issue, I'd have to pretty much make React Native from scratch all on my own. So yeah, it took a long time. But here we are, hopefully most things should be there. I am not Facebook. I do not have the team that Facebook has. So this is not React Native exactly how Facebook made it, but hopefully it's similar enough that you won't notice.

I did try embedded React Native into Spotify. I couldn't actually get it to initialize properly, but I got a lot further than I expected. Embedding React Native has its advantages and disadvantages. You can expect React Native performance and reliability, as it is just React Native. You could probably use real React Native packages, since it is just React Native. And there are tons of resources online about React Native, so there's an already established ecosystem with it. However, there are some potential disadvantages as well. I'd have to look into it more to give a full list of disadvantages. But I'm not entirely sure how I would load arbitrary JavaScript and associated native code that comes with those extensions if they use React Native packages that include native Java code (which is pretty much all of them). Also, it runs on Hermes, not node.js. Not sure if that's necessarily a disadvantage, but it's something to keep in mind. Maybe one day I'll look into it again. And if I feel it's good enough, I'll make a 2.0 update of sorts. But that wouldn't be for a while, if ever.

## Final Thoughts

So that's a quick briefing on why this exists. I believe this will be better than the original version because it will allow anyone to add any feature to Spotify they want. Also, once the API is "finished", updating to later versions of Spotify should be easier. As all the extensions run on the same underlying JavaScript engine, those will never have to be updated. All that needs to update is the code that hooks into Spotify to provide the API. 

And hey, if anyone has a better name for this version, or a better way to distinguish the two, please let me know 🙏🙏. I feel like it's been confusing talking about both versions. They are fundamentally different. So I have the original Spotify Plus, and the extension Spotify Plus. idk man. 

I can't wait to see where this project goes and I hope that you guys will make some really cool things! As always, if you have any ideas or feedback, or find any bugs, don't hesitate to reach out and let me know!
